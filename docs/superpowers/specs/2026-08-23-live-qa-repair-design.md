# DSH Scientific Reading 实机缺陷修复设计

## 目标

修复 2026-08-22 实机验证确认的四类问题，并把真实 Bundle 启动纳入交付门禁：

1. Profile Bundle 安装后因 `schemastery` 导入名不符合 DSH 宿主惯例而无法启动；
2. `/sr/reading/<paperId>` 与 `/sr/reader/<paperId>` 始终返回 404；
3. 异步加载后侧栏仍显示“全部文献（0）”；
4. 普通桌面宽度下三栏布局、表格列宽和状态标签过于拥挤。

成功标准是：在不依赖开发注入的隔离 `DSH_HOME` 中，本地 tarball 能安装、真实 DSH
`0.1.0-rc.7` 能启动、核心 HTTP 路由与浏览器页面可用；完成全部门禁后，再把同一 tarball
持久安装到用户 `web` Profile，重启并复验 3080。

## 已确认根因

- `src/config.ts` 使用历史别名 `schemastery`；DSH rc.7 的宿主插件统一导入
  `@deepseek-ai/schemastery`。临时提供旧别名后隔离实例即可启动，证明不是 DSH 启动器故障。
- 两个阅读路由对形如 `/doi_...` 的剩余路径调用 `split('/')[0]`，得到空字符串。
- 文献总数标签在初始空状态下创建，`refreshList()` 更新 `state.papers` 后没有更新标签。
- 当前左栏固定 200 px、右栏固定 380 px，中栏还要容纳四列表格；嵌入 DSH 主界面后可用宽度不足。
- 现有 `verify:profile-bundle` 只证明安装与配置合成，`verify-live` 只证明开发注入实例的
  API/client，二者都没有证明 tarball 能被真实宿主导入。

## 方案选择

### 运行时依赖

采用 DSH 原生导入方式：把源码、构建产物和 peer 声明统一改为
`@deepseek-ai/schemastery`。这是 rc.7 内置插件的标准模式，也能复用宿主解析回退。

不采用以下方案：

- 把旧别名放入普通 dependencies：离线安装仍可能需要 registry metadata；
- 把 schemastery 打进 tarball：增加包体和重复依赖，偏离 DSH 插件共享宿主依赖的模型。

### 阅读路由

保持现有路由结构，只把剩余路径按 `/` 拆分后过滤空段，再取第一个 paper ID。浅读与精读
使用相同的解析规则，不引入新的路由框架。

### 文献页布局

视觉方向保持 DSH 的克制研究工具风格，不做重新设计：

- 左栏收窄为约 160 px；
- 中栏保持弹性并设置可读的最小宽度；
- 右栏使用约 340–500 px 的弹性宽度；
- 窄窗口优先提供主体横向滚动，不把标题、年份与 DOI 挤成不可读字符列；
- 表格固定列宽策略，状态和年份不换行，标题与 DOI 截断时保留完整 `title` 提示；
- 状态标签增加内边距、圆角与稳定的高对比文字；
- 总数标签在每次列表刷新后更新，搜索只过滤行，不改变“全部文献”的总数语义。

不在本阶段实现 Markdown 渲染器、侧栏折叠、分页或新的视觉主题。

## 验证架构

修复严格按测试先行执行。

1. **依赖契约测试**：锁定源码导入名、peer 名称和宿主 rc.7 兼容边界。
2. **路由回归测试**：用临时 `dataRoot` 和真实 route handler 验证浅读/精读页面均返回
   200，非法 ID 与缺失文件仍返回 404。
3. **客户端回归测试**：锁定异步计数更新、表格列宽和三栏弹性布局的关键结构，再生成
   `lib/client.js`。
4. **离线门禁**：运行 build、package、fake DSH、工具/路由挂载与凭证边界测试。
5. **隔离真实启动**：在临时 `DSH_HOME` 中打包并安装 tarball，清除飞书凭证，启动真实
   DSH rc.7 到独立端口，验证根页面、client 包、论文列表/详情和阅读页面；退出进程并安全清理。
6. **浏览器视觉验证**：在隔离实例检查文献标签、总数、搜索、详情、阅读链接和普通桌面
   宽度布局；不触发下载、解析、精读或飞书写入。

`verify-live` 将补充浅读页面检查；隔离启动门禁必须覆盖真实模块导入，不能再以
`--dump-config` 成功代替启动成功。

## 用户 Profile 注入顺序

持久安装不是前置步骤。只有上述 1–6 全部通过后才执行：

1. 记录用户 `web` Profile 的 package/lock/patch 快照；
2. 使用已经通过隔离验收的同一 tarball 执行 `dsh plugin --profile web add`；
3. 停止当前 3080，重启真实 `web` Profile；
4. 重跑 HTTP、`verify-live` 和浏览器视觉验证；
5. 如果启动失败，恢复安装前快照并重启原 Profile。

注入与重启期间允许现有 DSH 会话中断。整个阶段不进行真实飞书写入，不提交密钥、用户
数据目录或论文资产，也不推送远端。

## 变更边界

预计只修改：

- `src/config.ts` 及生成的 `lib/config.js`/类型产物；
- `src/routes.ts` 及生成产物；
- `client/client.js` 及 `lib/client.js`；
- `package.json`、lockfile 与对应测试；
- Profile Bundle/上线验证脚本和必要的中文交接说明。

不改 Python 引擎业务逻辑、不改飞书字段结构、不重新生成文献内容、不升级 DSH。
